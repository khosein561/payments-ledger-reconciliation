# Payments Ledger & Reconciliation

A synthetic payments data platform that models the core workflow of a finance-data backbone:

1. **Ingest** payment events (Stripe-style webhooks) safely: signed, de-duplicated, retry-proof.
2. **Record** them in a **double-entry ledger** that the *database itself* refuses to corrupt.
3. **Reconcile** the ledger every day against two outside records (processor settlement file, bank file), classify every disagreement, and report it.
4. **Prove** it works: the data generator plants known errors, and the reconciler is scored against that answer key.

**Test mode only.** The project uses synthetic data and contains no real credentials or customer information. The application refuses to start with a live Stripe key.

Other measured facts:

- 910 simulated events ingested; end-to-end demo ≈ 6 seconds.
- **94 automated tests pass** (~16 s) against a real PostgreSQL (not mocks), because the main guarantees live in the database.
- Re-running the demo is idempotent: every event is reported `duplicate`, row counts are unchanged.
- Mutation checks confirmed that removing idempotency behavior or balance enforcement caused the focused tests to fail.
- `dbt build`: 10/10 models + tests pass; deliberately corrupting the ledger makes the custom dbt tests fail.
- Outage validation: stopping PostgreSQL under a running server returned HTTP 503; after restart, the sender retry was processed exactly once. Details are in [`docs/failure_drills.md`](docs/failure_drills.md).

## Architecture

```text
Stripe (test) ──POST /webhook──► FastAPI ─ verify HMAC signature ─ redact PII
                                    │
                         webhook_events (PK=event id)  ← dedupe
                                    │
                         handle_event → create_entry → journal_entries + postings
                                    │ (Postgres: balanced at COMMIT, append-only)
                  failure ──► dead_letter_events ──► replay

daily:  processor_YYYY-MM-DD.csv ┐
        bank_YYYY-MM-DD.csv      ┴► load (validated) → reconcile → DQ gate → dbt tests → report → notify
```

Details and the reasoning behind each choice: [`docs/architecture.md`](docs/architecture.md).

## Quickstart

Requirements: Python 3.11+, and PostgreSQL 16 (easiest via Docker).

```bash
cp .env.example .env                    # then edit POSTGRES_PASSWORD (and keep STRIPE keys as test-mode placeholders)
docker compose up -d postgres           # or use any Postgres 16 you already have
python -m venv .venv && source .venv/bin/activate
pip install -e ".[dev]"

python -m ledger migrate                # create schema, seed the chart of accounts
python -m ledger demo                   # full end-to-end run + score against the answer key
pytest                                  # 94 tests (creates and drops its own throwaway database)
```

Run the webhook API and send it a signed test event:

```bash
python -m ledger serve                  # http://127.0.0.1:8000  (GET /healthz)
# With the Stripe CLI (test mode): stripe listen --forward-to localhost:8000/webhook
# (put the whsec_... it prints in .env as STRIPE_WEBHOOK_SECRET)
```

dbt (optional): `cd dbt && dbt build` with `DBT_PROFILES_DIR=.` and the `POSTGRES_*` variables exported. Install the **stable** `dbt-postgres` release.

## Design decisions in one paragraph each

- **Integer cents, never floats.** Exact arithmetic; floats are rejected in code and the column is `BIGINT`.
- **Append-only ledger + reversing entries.** History is never rewritten; corrections are new entries that mirror old ones.
- **Database-enforced invariants.** Balanced entries (deferred constraint trigger), immutability (triggers), uniqueness (indexes), least privilege (roles). Application bugs cannot silently corrupt the books.
- **Idempotency everywhere.** Webhook id is a primary key, entry `source_event_id` is unique, settlement rows are unique per file/row, reconciliation replaces a date's run. Retrying anything is safe.
- **Fail loudly, in the right direction.** Temporary failure → 503 so the sender retries. Permanent failure → dead-letter + 200 so it doesn't retry forever.
- **Measured correctness.** An answer key makes "it works" a number.

## Scope and limitations

- The Docker Compose stack, optional Airflow service, Airflow DAG execution, and live Stripe delivery have not all been exercised end to end. PostgreSQL, the Python application, pytest, and dbt were run directly.
- Synthetic data: USD only; a simplified fee model (2.9% + 30¢); one processor; no FX, chargebacks/disputes or multi-currency; one bank account.
- Single node. No horizontal scaling, no queue between the HTTP endpoint and the database (at larger scale you would acknowledge fast and process from a queue).
- Role grants are defined and tested in SQL, but the Compose setup connects as one admin user for simplicity.
- Matching is deterministic (exact, then ±3-day tolerance); there is no fuzzy matching on references.
- dbt was verified with a pre-release build in the build environment; use the stable release.
